CommerceWorker serves its workspace tools to [Model Context Protocol](https://modelcontextprotocol.io)
clients at `https://app.commerceworker.com/mcp`. They are the
tools of [the assistant](/guides/assistant/), so a client can check what needs attention, find and
read orders and carts, and, with the right role, decide approvals, cancel orders, or build a
[cart](/guides/carts/) and submit it as an order. Each person is limited to
what their role allows.

The server is stateless: every request is answered by a fresh server that lists only the tools
the caller's role can use. It speaks streamable HTTP: the 2026-07-28 revision of the protocol,
and the 2025 revisions (2025-11-25 and earlier) served the same stateless way. Another agent that speaks Agent2Agent rather than MCP
connects at `/a2a`; see [A2A endpoint](/reference/a2a/). AI shopping platforms that buy from you use a separate endpoint and credential; see [Agentic checkout (UCP)](/reference/ucp/).

## Connecting

### Claude and Claude Desktop

Add a custom connector with the URL `https://app.commerceworker.com/mcp`. The client discovers the
authorization server, registers itself and opens CommerceWorker's consent page in your browser:

1. Sign in with your own account. Two-factor sign-in applies.
2. Check which app is asking and where access will be sent. An app that registered itself is
   marked as unverified; an app on your own computer gets an extra warning.
3. Choose a role. You are offered your own role and the roles below it, lowest first, and the
   lowest (`viewer`) is selected. `admin` is never offered, so a connected app can't use `draft_plugin`; an admin API token can. That role is the grant's scope.
4. Select **Connect**. **Cancel** refuses the app.

### Claude Code

```bash
claude mcp add --transport http commerceworker https://app.commerceworker.com/mcp
```

Claude Code runs the same browser flow the first time you use the server. To skip the browser, pass
an [API token](/guides/team-and-roles/#api-tokens):

```bash
claude mcp add --transport http commerceworker https://app.commerceworker.com/mcp \
  --header "Authorization: Bearer cmw_live_…"
```

### Cursor and other clients

A client that takes a URL and headers can send `Authorization: Bearer cmw_live_…` with every
request. In Cursor's `mcp.json`:

```json
{
  "mcpServers": {
    "commerceworker": {
      "url": "https://app.commerceworker.com/mcp",
      "headers": { "Authorization": "Bearer cmw_live_…" }
    }
  }
}
```

A client that runs OAuth itself starts from the `401` a request without a token gets: its
`WWW-Authenticate` names the resource metadata and the scopes, `viewer approver operator` (the
roles an app can be granted). It finds the authorization server from
`/.well-known/oauth-protected-resource/mcp`. It registers with dynamic client registration at
`/oauth/register` or with a Client ID Metadata Document (an `https` `client_id`), sends the person
to `/oauth/authorize` (authorization code with PKCE, `S256`, required of every client, including
one that registered with a secret) and exchanges the code at `/oauth/token`. The consent page honours
`max_age` and `prompt=login` on the authorization request: a person who signed in longer ago than
`max_age` seconds, or whom the app asked to sign in again, is asked to sign in again before they
approve. A request without a PKCE challenge is sent back to the app with `error=invalid_request`.
An app ends its own connection with an RFC 7009 revocation: `POST /oauth/token` with `token` (and
`token_type_hint`, `client_id`) and no `grant_type`; a refresh token ends the whole connection. A refresh token works
once: each refresh returns a new one. Retrying the old one within a minute (an answer that never
arrived) still works; presenting it again later revokes the connection, since only a copy would.

A client or directory that discovers servers before connecting can read the
[Server Card](https://modelcontextprotocol.io/seps/2127-mcp-server-cards) at
`https://app.commerceworker.com/mcp/server-card`, listed in `/.well-known/ai-catalog.json`. It names the
server, the endpoint and the protocol revisions it speaks. It lists no tools: those depend on who
connects, so a client learns them once connected.

A token carries the role it was created with and its expiry. `/mcp` accepts the same bearer
credentials as the [REST API](/reference/rest-api/): `cmw_live_` tokens. These work on `/a2a` too. A bearer that isn't a valid token is `401`, and an expired token is
refused (`401` with the reason), as there.

## Tools

A client sees only the rows its role can use. **Write** tools are the ones the
assistant stops to confirm; over MCP they take two calls, described next.

<McpTools />

Each tool has a title, a description, a JSON input schema and an output schema. Results come back
as JSON text and as `structuredContent` that matches the output schema; a field not in the schema
may be added later, so a client should ignore fields it doesn't know. `assess_order` and
`propose_flow_change` wait on a model: a client that sends a progress token hears when they start.
A refusal from live data (nothing is waiting on that event, the approval is
already decided, the order has finished, you started the order and the workspace [separates approvals](/guides/team-and-roles/#approvals), a cart is locked or not priced yet) is returned as a tool error the model can read, not a
protocol error. Any other failure is a tool error saying CommerceWorker couldn't complete the call,
without the details. A tool the role can't use is not listed, and calling it by name fails as
unknown. On 2026-07-28 the tool list may be cached by the client for a minute.

## Actions wait for the person

An action (`decide_approval`, `decide_approvals`, `deliver_event`, `cancel_order`, `submit_cart`,
`publish_flow`, `publish_catalog`, `create_promotion`, `set_promotion_status`, the [price book](/guides/price-books/) writes (`create_price_book`, `set_price_book_status`, `put_price_book_entries`, `assign_price_book`, `put_contract_prices`), `set_fx_rate`,
`verify_tax_certificate`, `revoke_tax_certificate`, `set_credit_limit`, `adjust_credit`, the [company](#companies) tools (`create_customer`, `update_customer`, `set_company_status`, `put_company_members`, `remove_company_member`, `put_company_team`), the [budget](#budgets) tools (`put_budget`, `set_budget_status`), the [purchase order](#purchase-orders) tools (`submit_po`, `cancel_po`), the [quote](#quotes) tools (`send_quote`, `accept_quote`, `decline_quote`, `expire_quote`, `convert_quote`), the admin tools (`set_member_role`,
`set_approval_separation`, `set_plugin_enabled`, `approve_plugin`, `rollback_plugin`,
`uninstall_plugin`, and the [outside access](#outside-access) tools `delete_webhook_subscription`, `redeliver_webhook_delivery`, `revoke_integration`, `revoke_ucp_platform` and `set_ucp_settings`, and `set_storefront_settings`, which turns [hosted checkout](/guides/hosted-checkout/) on), `run_stock_review`, `start_order`, `restart_order`, `cancel_cart`, `test_flow` and the catalog writes marked as confirming [below](#catalog-writes)) never runs on the first call, whatever the client does. Those that need a step-up (approving, rolling back, uninstalling or turning on a plugin, and making someone an admin) are refused over MCP, which has no session to step up; an admin API token may still turn a plugin off. How the person
agrees depends on the client.

`create_promotion` takes `kind: "bxgy"` with a `bxgy` rule (buy `{skus?, qty}`, get `{skus?, qty, percent?}`, `repeat?`; see [Buy X, get Y](/guides/promotions/#buy-x-get-y)) and refuses one that can never apply, and an optional `condition`, a JSON Logic expression over a documented context, and a `conditionMessage` for a buyer whose order doesn't meet it; the call is refused, with the reason, for a variable or operator the [promotions guide](/guides/promotions/#conditions) doesn't list, and the person's card shows the condition as written.

### Clients that ask their person

A client on the 2026-07-28 revision that declares form elicitation is asked to confirm. The
first call changes nothing and returns `input_required` with one elicitation, `confirm`: its
message is the preview (what will happen), and it asks for `{ "confirm": true }`. The client shows
it to the person, then retries the same call with their answer and the `requestState` it was
given. The action runs only if the person accepted with `confirm: true`; a decline, a cancel or
any other answer is a tool error, nothing happens, and that request state is used up. The same
rules as a code apply to the request state: it belongs to the same person, tool and input, lasts
5 minutes and works once. It is not a code: sent as `confirmation` it is refused, a code from the
two-call flow is refused as request state, and on a client that elicits any `confirmation` is
refused. So a model can't confirm on the person's behalf; what remains trusted is the client,
which shows the question and reports the answer.

### Other clients: two calls

Any other client, including every 2025-era one, gets a preview and a code. The first call
changes nothing and returns:

```json
{
  "preview": { … },
  "confirmation": "cfm_…",
  "expiresAt": 1760000000000,
  "next": "Nothing has happened yet. …"
}
```

The `preview` is what the assistant's confirm card shows: the order or flow, and where the
action leads. If the action is blocked (for example, you started the order and the workspace
separates approvals), the call returns a tool error with the reason and no code. The tool
descriptions and the server's instructions tell the model to show the preview to the person and to
call again only once they agree. Here the model relays the code, so it is the model that is
trusted to ask: prefer a client that elicits for anyone who can approve, cancel or publish.

The action runs when the same person calls again with the same input plus `confirmation`, within
5 minutes. A code works once. A code used by someone else, for another tool or with a different
input (key order doesn't matter), or one that expired or was used, is refused with a tool error;
call without it for a new preview. The role and the order's state are checked again when the
action runs. A `submit_cart` code is also held to the cart as the preview showed it: if anything
changed the cart in between (a `change_cart`, someone on the cart's page), the confirmed call is
refused with "The cart changed since you confirmed; preview it again" and nothing is submitted.
The same holds when the person confirms through an eliciting client.

Reads, `propose_flow_change`, `draft_plugin`, `draft_product_content`, `create_cart`,
`change_cart` and `create_checkout` do not take a code: a cart is only a draft of an order until `submit_cart`, and a
product draft changes nothing until a person publishes it. Over [A2A](/reference/a2a/), typed skills
(and `place_order`) run directly, as REST calls do, and `chat` already asks for `{ "confirm": true }`.

Annotations also tell a client when to confirm:

| Tools | Hints |
|---|---|
| Reads and `propose_flow_change` | `readOnlyHint: true` |
| `draft_plugin`, `draft_product_content`, `create_cart`, `change_cart`, `create_flow`, `duplicate_flow`, `archive_flow` | save a draft (nothing runs until an admin approves the plugin, someone publishes the product's drafts or submits the cart): not read-only, not destructive, not idempotent |
| `decide_approval`, `decide_approvals`, `cancel_order`, `submit_cart`, `publish_flow`, `publish_catalog`, `uninstall_plugin` | `destructiveHint: true`; all but `publish_flow` are also `idempotentHint: true` |
| The [outside access](#outside-access) tools that remove or revoke, `set_ucp_settings` and `set_storefront_settings` | `destructiveHint: true` and `idempotentHint: true` |
| The [catalog's writes](#catalog-writes) that go live or take something down, and `discard_product_edits` | `destructiveHint: true` |
| `deliver_event`, `run_stock_review`, `start_order`, `restart_order`, `cancel_cart`, `test_flow`, `create_promotion`, `set_promotion_status`, `verify_tax_certificate`, `revoke_tax_certificate`, `create_customer`, `put_company_team`, `set_member_role`, `set_approval_separation`, `set_plugin_enabled`, `approve_plugin`, `rollback_plugin` | writes, not destructive |
| `set_fx_rate` | `destructiveHint: true` and `idempotentHint: true`: it replaces the rate buyers pay by, and the same rate again changes nothing |
| `set_company_status`, `remove_company_member` | `destructiveHint: true` and `idempotentHint: true`: closing or rejecting a company and removing a member are final, and the same move again changes nothing |
| `update_customer`, `put_company_members` | writes, not destructive, `idempotentHint: true`: the same input again changes nothing |
| `set_credit_limit` | `destructiveHint: true` and `idempotentHint: true`: it replaces the limit a customer orders on account by, and the same limit again changes nothing |
| `adjust_credit` | a write, not destructive and not idempotent: each confirmed call adds one ledger entry, which another adjustment undoes |
| `create_price_book` | a write, not destructive: it adds a draft |
| `assign_price_book` | `idempotentHint: true`: assigning again is refused, as is taking away what isn't assigned |
| `put_price_book_entries`, `put_contract_prices`, `set_price_book_status` | `destructiveHint: true` and `idempotentHint: true`: they replace what buyers pay (or, archiving, retire a book for good), and the same input again changes nothing more |
| `set_budget_status` | `destructiveHint: true` and `idempotentHint: true`: archiving a budget is final, and the same move again changes nothing |
| `put_budget` | a write, not destructive, not idempotent: without a `budgetId` it adds another budget |
| `submit_po`, `cancel_po` | `destructiveHint: true` and `idempotentHint: true`: submitting starts an order (once per purchase order) and cancelling cancels it; the same call again changes nothing |
| `create_po_draft`, `update_po_draft` | writes without a confirmation, not destructive: a draft starts nothing |
| `create_checkout` | a write without a confirmation, not destructive, not idempotent: each call makes a checkout and its one-time link, and nothing is ordered until the buyer completes it |
| `send_quote`, `accept_quote`, `decline_quote`, `expire_quote` | `destructiveHint: true` and `idempotentHint: true`: a sent quote can't be edited, accepting or ending one changes what a company pays, and the same move again changes nothing |
| `convert_quote` | `destructiveHint: true`, `idempotentHint: true` and `openWorldHint: true`: it makes a PO draft or starts an order, once per quote |
| `redeliver_webhook_delivery` | `idempotentHint: true` and `openWorldHint: true`, not destructive: it sends the receiver the same delivery again, which a receiver that dedupes by delivery id handles once |
| `create_quote`, `update_quote`, `revise_quote` | writes without a confirmation, not destructive: a draft prices nothing |

`assess_order` set `openWorldHint: true` (a started order runs its flow for real):
cancelling voids payments and cancels shipments with the carrier, a submitted cart's order runs its
flow (payments and shipping included), the stock review places reorders with suppliers, and an
assessment may fetch an `https` image. The other tools set it to `false`.

## Admin reads

An admin token (a connected app is never offered `admin`) also has nine reads that mirror the
REST API's, and they return the same thing: `list_audit_events` (by group, paging back with `before`,
or from a `seq` with `after`, oldest first), `verify_audit_trail` (checks the hash chain a batch at
a time; `next` is where to continue), `list_plugins` and `get_plugin_usage` (what still depends on
a plugin), and `list_webhook_subscriptions` and `list_webhook_deliveries`, `list_integrations` and
`get_ucp_settings` (agentic checkout's settings and the platforms let in) and `get_storefront_settings` (hosted checkout's). None of them returns a
signing secret, a key or anything sealed. Their annotations are `readOnlyHint: true`. Lower roles
aren't offered them.

## Approvals decided by votes

`decide_approval` and `decide_approvals` cast a vote on an [approval that several people
decide](/guides/approvals-and-events/#who-approves-and-how-many-votes). Both take an optional
`onBehalfOf`, a company member's id, for staff recording that member's vote (the card says whose
vote it is and that you recorded it). `get_order` names each open approval's `approvers` and
`tally`. Confirmed, a call answers `outcome` (`recorded` while more votes are needed and the order
still waits, then `approved` or `rejected` once the votes decide it) and `tally` (like `1 of 2`);
`decide_approvals` gives each approval's own `outcome` and `tally` in `results`. The same refusals
hold as over REST, and each vote is audited as `approval.decided` with `onBehalfOf`, `outcome` and
`tally`. A rejection ends the vote.

## Companies

A business customer's [company](/guides/companies/), its members and its teams are three reads and six
writes, REST's `/api/v1/companies` and `/api/v1/customers` routes by another way in: they run the same code, so they
refuse what REST refuses and write the same audit entries (`customer.created`, `customer.updated`,
`company.status_changed`, `company.members_saved`, `company.member_removed`, `company.team_saved`).
All need the `operator` role, and an API token may use them.

| Tool | Does |
|---|---|
| `list_companies` | A page of companies by name: `status`, `search` (part of the name, legal name or id), `cursor` and `limit` (at most 100); answers `companies`, `total` and the next `cursor` (`null` at the end). `readOnlyHint: true` |
| `get_company` | `{ companyId }`: the company and its team tree. `readOnlyHint: true` |
| `list_company_members` | `{ companyId, status?, role?, teamId?, cursor?, limit? }`: a page of members by name, with their role, team, status and own order limit. Names and emails are personal data. `readOnlyHint: true` |
| `create_customer` | `{ name, email, kind?, tier?, terms?, company? }`: adds a customer; a business one (the default kind) also gets its company, active, with `company.legalName`, `taxId` and `parentCompanyId` if given. Refuses an email another customer has |
| `update_customer` | `{ customerId, name?, email?, kind?, tier?, terms? }`. The credit limit is not a field. A kind change is refused while it would leave a customer without its company or a company without its customer |
| `set_company_status` | `{ companyId, status }`: `pending` to `active` or `rejected`, `active` and `suspended` to each other, either to `closed`; `rejected` and `closed` are final |
| `put_company_members` | `{ companyId, members }`, up to 100 `{ email, name, role?, teamId?, orderLimit?, status? }`. A new member starts `invited` or `active`; an email already a member is changed, and a field left out stays as it was (`null` clears a team or limit) |
| `remove_company_member` | `{ companyId, memberId }`: final; the member's record stays for the orders they placed |
| `put_company_team` | `{ companyId, name, teamId?, parentTeamId? }`: adds a team, or renames and moves one with the teams under it. Teams nest up to six deep |

Each write confirms, as [above](#actions-wait-for-the-person). The preview says what the move does to orders and
counts members without naming them, and the audit entry does the same.

## Credit accounts

`get_credit_account` (viewer and above, `readOnlyHint: true`), `set_credit_limit` and `adjust_credit` (admin)
are REST's `GET /api/v1/customers/:customerId/credit`, `POST …/credit/limit` and `POST …/credit/adjustments`,
and the customer page's **Credit** section runs the same code, so they refuse what REST refuses and write the same
audit entries (`credit.limit_set` and `credit.adjusted`). `get_credit_account` takes `{ customerId, after?, limit? }`
and returns the `limit`, the `balance` owed, `held` (what open orders have claimed), `available` (limit less balance
less held), all in USD, and a page of the ledger, newest first: each entry has its `kind` (`charge`, `settle`,
`reverse` or `adjust`), `amount`, the `balanceAfter` it left, its order, and for an adjustment its `reference` (who)
and `note` (the reason). `next` is the cursor for the earlier entries; pass it as `after`. `set_credit_limit` takes
`{ customerId, limit }` and `adjust_credit` takes `{ customerId, amount, reason }`: a negative `amount` lowers what is
owed (a credit memo, or a payment received outside CommerceWorker) and a positive one raises it. A reason is required,
since it is what the ledger shows. Both confirm, as [above](#actions-wait-for-the-person): the preview shows the account
now and after, and a limit under what is owed and held warns that new orders on account are refused until it is paid
down. They are refused up front for an unknown customer or one that isn't a business customer, and `set_credit_limit` for a company that is suspended, closed or rejected. Only a person confirms
them: over REST an API token is refused (`403`), and a typed A2A skill never runs them. Over REST an `Idempotency-Key`
makes a retried adjustment record once.
## Price books

`list_price_books`, `get_price_book` and `preview_price` (viewer and above, `readOnlyHint: true`) and
the writes `create_price_book`, `set_price_book_status`, `put_price_book_entries`, `assign_price_book`
and `put_contract_prices` (operator) are REST's `/api/v1/price-books` routes, `/api/v1/price-preview`
and `/api/v1/customers/:customerId/contract-prices`, and the **Price books** pages run the same code,
so they refuse what REST refuses and write the same audit entries (`price_book.created`,
`price_book.status`, `price_book.entries`, `price_book.assigned`, `price_book.unassigned` and
`contract_price.saved`). Lists and entries page with `next`, passed back as `after`. Each write
confirms, as [above](#actions-wait-for-the-person): the preview says what changes and for whom, and
that a book prices nothing until it has entries, is assigned and is active inside its dates. It is
refused up front for an unknown book, customer or SKU, an impossible move (a draft can't become
inactive; an archived book can't change), a code already taken, or an entry with both a price and a
percentage. Only a person confirms them: over REST an API token is refused (`403`), and a typed A2A
skill never runs them. See [Price books](/guides/price-books/).

## Budgets

A company's [budgets](/guides/companies/#budgets) are one read and two writes, REST's
`/api/v1/companies/:companyId/budgets` routes by another way in. They run the same code, so they refuse
what REST refuses and write the same audit entries (`budget.saved`, `budget.status_changed`). Reading
needs the `viewer` role; the writes need `operator`, and an API token may use them (none changes what a
buyer pays: a budget holds an order only through a flow's Budget check).

| Tool | Does |
|---|---|
| `list_budgets` | `{ companyId, teamId?, status?, cursor?, limit? }`: a page of the company's budgets by name (at most 100 a page); each with its `amount`, `period`, `enforcement`, `status`, `teamId`, the `window` it counts now (`start` and `end`, `end` null for a one-time budget; null before the budget starts), what that window has `spent` and what is `remaining`. Answers `budgets`, `total` and the next `cursor` (`null` at the end). `readOnlyHint: true` |
| `list_budget_spend` | `{ companyId, budgetId, cursor?, limit? }`: a page of the budget's spend ledger, newest first (at most 100 a page); each entry with its `orderId`, `amount` (as committed: a commit given back keeps its amount and reads `reversed`), the `windowStart` it counts in, `at` and `status` (`committed` or `reversed`). Answers `entries`, `total` and the next `cursor` (`null` at the end). A `budgetId` that isn't the named company's reads empty. `readOnlyHint: true` |
| `put_budget` | `{ companyId, name, amount, period?, teamId?, enforcement?, startsOn?, budgetId? }`: adds a budget (`period` is required; `enforcement` defaults to `advisory`, `startsOn` to today in UTC), or with a `budgetId` changes its name, amount and enforcement. Its period, team and start can't change; a closed or rejected company's budgets aren't changed; a company holds at most 100 |
| `set_budget_status` | `{ companyId, budgetId, status }`: `active` and `paused` to each other, either to `archived`, which is final |

Amounts are in the base currency. The previews say what the budget does to orders.

## Purchase orders

A company's [purchase orders](/guides/purchase-orders/) are two reads and four writes, REST's
`/api/v1/purchase-orders` routes by another way in. They run the same code, so they refuse what REST
refuses and write the same audit entries (`purchase_order.created`, `.updated`, `.submitted`,
`.cancelled`). Reading needs the `viewer` role; the writes need `operator`, and an API token may use
them. Drafting and editing a draft need no confirmation; submitting and cancelling do.

| Tool | Does |
|---|---|
| `list_purchase_orders` | `{ companyId?, status?, buyerId?, search?, from?, to?, cursor?, limit? }`: a page of purchase orders, newest first (at most 100 a page); `from` and `to` are days (`YYYY-MM-DD`, UTC, inclusive). Answers `purchaseOrders`, `total` and the next `cursor` (`null` at the end). `readOnlyHint: true` |
| `get_purchase_order` | `{ poId }`: one purchase order with its `lines`, ship-to, notes and the `orderId` it started. `readOnlyHint: true` |
| `create_po_draft` | `{ companyId, poNumber, lines, buyerId?, currency?, shipTo?, notes?, quoteId? }`: saves a draft. The number is unique within the company; the company must be active and the buyer an active member of it |
| `update_po_draft` | `{ poId, poNumber?, buyerId?, currency?, shipTo?, notes?, quoteId?, lines? }`: changes a draft; `lines` replaces the whole list. Refused once the purchase order is submitted |
| `submit_po` | `{ poId, flowId? }`: submits a draft and starts its order on the B2B purchase order flow (or `flowId`), once however often it is called |
| `cancel_po` | `{ poId, reason? }`: cancels a purchase order that hasn't ended, and its order if it is running |

## Quotes

A company's [quotes](/guides/quotes/) are two reads and eight writes, REST's `/api/v1/quotes` routes
by another way in. They run the same code, so they refuse what REST refuses and write the same audit
entries (`quote.created`, `.updated`, `.sent`, `.accepted`, `.declined`, `.expired`, `.revised`,
`.converted`). Reading needs the `viewer` role; the writes need `operator`, and an API token may use
them. Drafting, editing and revising need no confirmation; sending, accepting, declining, ending and
converting do. Amounts are in the base currency.

| Tool | Does |
|---|---|
| `list_quotes` | `{ companyId?, status?, rootId?, search?, cursor?, limit? }`: a page of quotes, newest first (at most 100 a page). Superseded versions are left out unless a `status` or a `rootId` (every version of one negotiation) is given. Answers `quotes`, `total` and the next `cursor`. `readOnlyHint: true` |
| `get_quote` | `{ quoteId }`: one quote with its `lines` (SKU, the most it covers, list and quoted price), `versions`, expiry and what it was converted into. `readOnlyHint: true` |
| `create_quote` | `{ companyId, name, lines, buyerId?, expiresOn?, notes? }`: saves a draft. Lines are `{ sku, qty, unitPrice, name? }`, one per SKU, each a product; `expiresOn` is a day (`YYYY-MM-DD`), the last the prices count (UTC) |
| `update_quote` | `{ quoteId, name?, buyerId?, expiresOn?, notes?, lines? }`: changes a draft; `lines` replaces the whole list. Refused once the quote is sent |
| `revise_quote` | `{ quoteId }`: starts the next version of a sent, declined or expired quote as a draft and supersedes the old one; the same call again returns that version |
| `send_quote` | `{ quoteId }`: sends a draft; it needs an expiry day ahead |
| `accept_quote` | `{ quoteId, note? }`: records that the company accepted a sent quote that hasn't expired |
| `decline_quote` | `{ quoteId, reason? }`: records that the company declined a sent quote, or withdraws a draft |
| `expire_quote` | `{ quoteId }`: ends a sent or accepted quote now |
| `convert_quote` | `{ quoteId, to?, poNumber?, flowId? }`: turns an accepted quote into a purchase order draft (`to: po`, the default when the company has purchase orders) or an order (`to: order`), once however often it is called |

## Exchange rates

`list_fx_rates` (operator and above, `readOnlyHint: true`) and `set_fx_rate` (admin) are REST's
`GET /api/v1/fx-rates` and `POST /api/v1/fx-rates/:currency`, and the Commerce page's **Exchange rates**
table runs the same code, so they refuse what REST refuses and write the same audit entry
(`fx.rate_set`, with the old and new rate and the change). `list_fx_rates` shows each currency's rate
(units per one USD), when it was set and whether the daily ECB refresh or a person set it; a currency the
workspace is set up to sell in but has no rate for yet shows with none. `set_fx_rate` takes
`{ currency, rate }` and confirms, as [above](#actions-wait-for-the-person): the preview shows the rate now
and the new one, the change as a percent, flags a change of 10% or more, and says that orders already
priced keep their rate. It is refused up front for `USD`, a currency the workspace has no rate for and isn't
set up to sell in, or a rate that isn't a positive number within bounds. Only a person confirms it: over
REST an API token is refused (`403`), and a typed A2A skill never runs it. A rate set this way holds until
someone changes it: the daily refresh leaves it and keeps refreshing the other currencies.

## Outside access

An admin can also take away what lets a system into the workspace, change agentic checkout, turn
hosted checkout on and send a webhook delivery again. These six are REST's `DELETE /api/v1/webhook-subscriptions/:id`,
`POST /api/v1/webhook-deliveries/:deliveryId/redeliver`,
`DELETE /api/v1/integrations/:id`, `DELETE /api/v1/ucp/platforms/:id`, `POST /api/v1/ucp/settings` and
`POST /api/v1/storefront/settings`, run by the same code, so they refuse what REST refuses and write the
same audit entries (`webhook.unsubscribed`, `webhook.redelivered`, `integration.revoked`, `ucp.platform_revoked`, `ucp.settings`
and `checkout.settings`), recorded as made over MCP. Each confirms, as
[above](#actions-wait-for-the-person).

| Tool | Role | What it does |
|---|---|---|
| `delete_webhook_subscription` | admin | Removes a subscription and its record of deliveries. The preview shows where it posts (without any query), the events it takes and its last delivery. Refused up front for an unknown id. |
| `redeliver_webhook_delivery` | admin | Sends a `failed` or `delivered` delivery to its receiver again, with the same delivery id and payload and the subscription's current signature (see [Outbound webhooks](/guides/outbound-webhooks/#redelivering)). The preview shows where it goes (without any query), the event and its last outcome. Refused up front for an unknown delivery, one still waiting for its first attempt, or one whose subscription is gone. |
| `revoke_integration` | admin | Revokes an integration at once, both its secrets. The preview shows its name, when it was last used and whether it starts orders. Refused up front for an unknown or already revoked one. |
| `revoke_ucp_platform` | admin | Revokes an AI shopping platform's key. Its checkouts and orders stay. The preview shows its name, profile and when it was last used. Refused up front for an unknown or already revoked one. |
| `set_ucp_settings` | admin | Sets the checkout flow (`null` turns agentic checkout off), the legal links and the order page URL, taking the same body as REST and replacing all three. The preview says what changes from now; it is refused up front when the flow is unpublished or never authorizes a card. |
| `set_storefront_settings` | admin | Turns [hosted checkout](/guides/hosted-checkout/) on or off, names the flow that prices it (`null` uses agentic checkout's) and whether the buyer may change the lines, taking the same body as `POST /api/v1/storefront/settings` and replacing all three. The preview says what the checkout is priced by; turning it on is refused up front when there is no flow, or it is unpublished or never authorizes a card. Audited as `checkout.settings`. |

Creating or rotating a subscription, an integration or a platform stays on REST and in the app: it
issues a secret or key that is shown once, and only a person or a token they hold should see it.
No tool, preview or result carries one.

## Catalog reads

Every role can also read the product catalog, with ten tools that mirror the REST API's catalog
`GET` routes and return the same thing, as the catalog Worker answers them: `get_product` and
`get_product_sheet` (its live and feed versions, staged edits, drafts, gaps and history),
`find_product_by_alias` (the key behind `sku:…`, `gtin:…` or `slug:<locale>:…`),
`list_product_types`, `list_catalog_channels`, `list_categories`, `list_catalog_feeds` (newest
first; `limit` 1 to 100, 20 unset), `get_catalog_feed`, `catalog_board` (the product editor's counts
per column and gap kind, with the latest and the running feed) and `catalog_board_column` (one
column's products, a page at a time: `limit` 1 to 100, 50 unset, and the `cursor` the last page
returned; `kind` narrows the gaps column). A product, alias, sheet or feed the catalog doesn't have
is a tool error, where REST answers `404`. `find_products` is not one of these: it reads the stock
list. Their annotations are `readOnlyHint: true`.

## Catalog writes

An operator can also change the catalog, with tools that mirror the REST API's catalog writes: the
same bounds (500 items a call), roles and audit entries, which record the call as made over MCP.
`draft_product_content` and `publish_catalog` are covered above. Writing products, categories or a
feed changes the live catalog at once (each stored product publishes within the minute), not a
draft, so those confirm like publishing does.

| Tool | Role | Confirms | What it does |
|---|---|---|---|
| `put_catalog_type` | operator | no | Adds a product type, or its next version (additive only). Nothing is published until products use it. |
| `put_catalog_channel` | operator | no | Adds or changes a channel; a changed currency or locale list reaches published pages on the next reindex. |
| `stage_product_edits` | operator | no | Stages edits to products' fields. Nothing is live until `publish_catalog`. |
| `discard_product_edits` | operator | no | Drops staged edits or the assistant's drafts (`what`), for one field or a whole product. |
| `put_catalog_products` | operator | yes | Creates or updates up to 500 products. The preview names the keys and says it writes live. |
| `delete_catalog_products` | operator | yes | Deletes up to 500 products. The preview says how many exist; it is refused when none do. |
| `put_catalog_categories` | operator | yes | Writes up to 500 categories and republishes the category tree. |
| `delete_catalog_categories` | operator | yes | Removes categories. Refused up front for an unknown code or a child left behind; the catalog refuses while products are in one. |
| `delete_catalog_type` | operator | yes | Removes every version of a type. Refused up front for an unknown type; the catalog refuses while a product uses it. |
| `start_catalog_feed` | operator | yes | Imports a CSV or NDJSON file given as text (`content`, up to 256 KiB; larger files stream over REST). The preview shows the format, rows and size. |
| `cancel_catalog_feed` | operator | yes | Stops a feed that hasn't finished; refused up front for one that has. |

A write the catalog refuses when it runs (a type still in use, a type version that removes
something) is a tool error carrying the catalog's reasons, where REST answers `409` or `400`.
Everything that confirms is `destructiveHint: true`, apart from `reindex_catalog` and
`rebuild_catalog_gaps`; `discard_product_edits` is too, since it drops work a person staged. Storing
a caller's own drafts (`POST /api/v1/catalog/drafts`) stays on REST: over MCP the assistant writes
drafts with `draft_product_content`, and a person's own text is staged as an edit. Accepting a draft
stays the Catalog page's button.

## Carts

`list_carts` and `get_cart` read the carts your team opens on the Carts page; a cart a customer
opened from their own purchasing system is not reached here. `get_cart` gives each line's
`lineId`, which `change_cart` names in `set_qty`, `set_qtys` (several lines in one op, all or
none) and `remove`, and the `shippingOptions` the
flow offers for the cart's `shipTo`, whose `id` `set_shipping_option` names (`set_ship_to` sets the
address). `change_cart` takes up to 20 `ops`,
applied in order as you, each priced again by the cart's flow; it stops at the first one the cart
refuses (a locked or ended cart, a line that is gone) and says how many went in. A cart's chat and
files are never served, and its title and line names come back as one short line each.
`submit_cart` also takes an optional `cartVersion` (the `version` you read), refused when the cart
has changed since; the confirmation holds it to the cart as previewed either way.

## Who did it

Each write is also an [audit log](/guides/team-and-roles/#audit-log) event, `via` MCP with the `tool`; read-only tools are not logged.

A write made over MCP is attributed to the person who approved the connection, with the channel:
`<email> via MCP`. That string is the approval's `by` or ends the cancel reason, as `<email> via
assistant` does for the panel (see [Who decided](/guides/team-and-roles/#who-decided)). A client
using an API token acts as `token:<name>`.

## Disconnecting

**Account** lists **Connected apps** (MCP clients and A2A agents alike): the app's name, whether it
connected over MCP or A2A, the address its access goes to, the role you granted and when it
connected.
**Disconnect** revokes the grant, and the app has to be connected again. Connecting and
disconnecting are recorded in the [audit log](/guides/team-and-roles/#audit-log) as
`oauth.app_connected` and `oauth.app_disconnected`. Access tokens last one hour and refresh
tokens 30 days.

## Security

- **One endpoint per token.** `/mcp`, `/a2a` and the [REST API](/reference/rest-api/#oauth-access-tokens)
  (`/api/v1`) are separate OAuth resources of one authorization server. A client requests `https://app.commerceworker.com/mcp` (a client that names no resource, and grants
  made before A2A existed, are for MCP), and the access token it gets is refused at `/a2a`; an
  A2A token, or one for the REST API, is likewise refused here. Each endpoint publishes its own metadata at
  `/.well-known/oauth-protected-resource/<path>`.
- **Role cap.** A grant is never higher than the role of the person who approved it, and the
  consent page offers no more. Pick the lowest role the client needs.
- **Checked on every request.** CommerceWorker re-reads the person each time, and that the connection
  still exists: disconnecting an app (or a revocation by the app itself) stops its access token
  within about a minute, though the token has not yet expired. A disabled or deleted
  person's grants stop working at once. The role is the lower of the one granted and the
  person's current role, so demoting someone narrows the apps they connected. A person whose role
  must use two-factor sign-in and hasn't set it up, or who is still on a temporary password, gets
  `403`.
- **Registration is limited.** An app registering itself may name up to 10 return addresses, and
  its `client_uri`, `logo_uri`, `policy_uri` and `tos_uri`, when given, must be `https` URLs. A
  `software_statement` is refused (`invalid_software_statement`): CommerceWorker verifies no
  registrar's signature, so it won't take claims on trust.
- **Credentials stay at the edge.** CommerceWorker resolves the caller before the request reaches the
  tools; `Authorization` and cookies go no further, and the model never sees a token.
- **Origin.** A request whose `Origin` is not an `http` or `https` origin is refused with `403`.
  Other origins are accepted on purpose. The Origin check in the MCP specification guards against
  DNS rebinding, where a web page reaches a server that trusts the browser it runs in. `/mcp` trusts
  no browser: every request needs a bearer token, which a browser never attaches by itself, and
  cookies are removed before the request reaches the tools. A page on another origin can't call it
  as you unless it already holds your token.
- **Rate limits.** Each caller (a person's grant or an API token) has 300 requests a minute on
  `/mcp`, and another 300 on `/a2a`; over that it answers `429` with `Retry-After: 60`.
  `/oauth/register` allows 10 requests a minute and `/oauth/token` 60, per address; over that it
  answers `429 { "error": "slow_down" }` with `Retry-After: 60`.
- **Tokens at rest.** Tokens are stored hashed and grant data encrypted.
