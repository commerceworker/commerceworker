# Roadmap

CommerceWorker began as a renamed order engine codebase (P0, done). The phases below turn it into the full platform. Each phase lifts code we already own: the platform packages for architecture and tooling, Commerce Worker v1 for domain logic. `docs/port-map.md` names the source for every item. Every phase builds on Cloudflare primitives and D1; nothing reintroduces Neon or Postgres.

## Carried over from the order engine

Open items in the order engine, unchanged from its original roadmap:

- **More channel adapters.** Shopify orders and EDI X12 850 purchase orders are in. Still to come: Amazon (an SP-API notification consumer and order fetch), 997 functional acknowledgements for EDI, and AS2/SFTP transport so partners can send without a provider in between.
- **Concurrent seller responses.** A marketplace order waits for one `seller.responded` per pass of its acceptance loop, so a second seller who answers in the gap gets `409` (`delivered: false`) and has to retry. Buffering early responses on the order would let every reply land the first time.
- **Exchange rates people can manage.** Production has a rate for USD only, and the Commerce page lists rates without editing them, so another currency needs a row inserted into `fx_rates` by hand. A rate editor for operators, or a daily job that fetches rates from a provider, would let orders in EUR, GBP or CAD through.
- **Smaller live updates on the order page.** Every OrderAgent `setState` broadcasts the whole state, the static `flow` graph and a 400-entry timeline included, four to six times per node. Sending the flow once and coalescing a node's reports into one update would cut socket traffic, but it changes the Workflow-to-agent reports and the state the order page reads, so it needs its own change.
- **Release approval.** Production deploys run in the `production` GitHub environment. Adding a required reviewer there would hold each merge to `main` until someone approves its deploy.
- **More of UCP.** Agentic checkout speaks UCP `2026-08-25` (checkout with shipping, orders, REST and MCP) and pays through Stripe. Still to come, roughly in order of what platforms ask for: catalog search and lookup (needs product titles, descriptions, media and variants on `products`, which the "not planned" list below rules out as PIM, so that would need revisiting); identity linking on the existing OAuth server (`{capability}:{scope}` scopes, RFC 7009 revocation, RFC 9207 `iss`); the discount extension mapped onto `price_rules`; pickup as a fulfillment method; checkouts in other currencies; AP2 mandates and the payment authentication extension, so a card that needs 3DS can finish instead of being refused; UCP as an A2A extension on the Agent Card; and verifying platforms' RFC 9421 request signatures as an alternative to API keys. Stripe PaymentMethods can't be bound to one checkout, which UCP's tokenizer handlers ask for; a Stripe shared payment token would be, once Stripe's preview API is enabled on the account.
- **ACP.** ChatGPT and Copilot check out through the Agentic Commerce Protocol. It can be a thin adapter on the same checkout core (`packages/core/src/checkout.ts`): `/checkout_sessions` mapped like `./ucp/`, payment by Stripe shared payment token (`payment_method_data[shared_payment_granted_token]` on API version `2026-09-30.preview`, a preview that must be enabled on the account), and a product feed. Stripe's hosted seller integration, where Stripe serves the protocol from an uploaded catalog feed and calls three hooks of ours, stays the cheaper route if a customer wants ACP only.
- **An event inbox on the order.** An event that arrives before its wait opens is refused (`409`, or `retry` for a Stripe event), and the sender has to try again: Stripe does for three days, a seller or a WMS might not. Holding early events on the OrderAgent and delivering them when the matching wait opens would let every one land the first time, and would also cover concurrent seller responses above.
- **Clear out the old test orders' documents.** Migration 0027 deleted the four test orders production ran on demo data, but their invoices and purchase orders are still in the `commerceworker-docs` R2 bucket under `orders/<id>/`, unreferenced. A one-off delete of those prefixes finishes the cleanup.

## Not planned

- **Neon, Postgres or Hyperdrive.** D1 and Durable Object SQLite are the data plane.
- **A multi-tenant pool, hostname dispatch and a control plane with billing.** Each customer is an isolated deployment from `deployments/`, provisioned by `scripts/provision.sh`.
- **Plan or feature gating.**
- **GraphQL.** REST and MCP are the two transports.
- **Workers for Platforms merchant functions.** Sandboxed plugins on Worker Loader cover custom code.
