# Configuration

Variables, secrets and bindings for the engine, web, catalog and delivery Workers, and the local dev files.

Each Worker is configured in its `wrangler.jsonc`. After changing one, regenerate its binding
types: `pnpm --filter @commerceworker/engine types`, `pnpm --filter @commerceworker/web types` or `pnpm --filter @commerceworker/catalog types` (the delivery Worker has no generated binding types: its bindings are typed in `src/catalog/env.ts` and core's `EdgeEnv`).

## Catalog variables

The catalog Worker has five variables and no secrets (`apps/catalog/wrangler.jsonc`); the delivery Worker, as the fleet deploys it, has neither variables nor secrets (`apps/delivery/wrangler.catalog.jsonc`, the catalog's bindings with the content stack off; `apps/delivery/wrangler.jsonc` is the content stack's template, whose bindings, variables and secrets are in the content docs):

| Variable | Default | Meaning |
|---|---|---|
| `DATA_JURISDICTION` | empty | Jurisdiction of the catalog's Durable Objects (`CatalogShard`, `CatalogMeta`, `CatalogFeeds`, `ListingIndexer`, `SearchShard`, `CatalogPublisher`): `eu` or `fedramp`, or empty for none; any other value throws on first use (`apps/catalog/src/config.ts`). The registry's `jurisdiction` sets it per deployment, and the catalog's R2 bucket takes the same one (`scripts/fleet.ts`). Local dev and tests leave it empty. Set it before the first product: a different value gives different object ids, so existing products are unreachable. See [Data residency](data-model.md#data-residency) |
| `FEED_CHUNK` | `25000` | Products one `FeedImport` split step reads before handing off to the next (a string; `25000` when unset or not a number, `FEED_CHUNK` in core). Lower it only in tests, where `apps/catalog/vitest.config.ts` sets `300` so a small feed spans several steps |
| `ORDERS_CHANNEL` | `web` | The channel code whose prices feed CommerceWorker's `products` table (`apps/catalog/src/orders.ts`, `publishKeys`): each active variant priced there in `BASE_CURRENCY` (`USD`) is upserted with its name and price. A channel in another currency writes nothing. UCP catalog search shows this channel too (`CatalogApi.ordersChannel()` returns it to the engine). Changing it applies to products as they next publish (or on `reindex`); rows already written stay. See [CommerceWorker's products](architecture.md#commerceworkers-products) |
| `GAP_REBUILD_DELAY_MS` | `0` | How long after a channel is changed or deleted (`CatalogShard.markGapsStale`), or after a shard that held products before the index first wakes (`backfillGaps`), a catalog shard's alarm starts recomputing its [product editor](product-editor.md) gap index. The tests set it to an hour and rebuild themselves (`rebuildGaps`, or by making the job due and running the alarm), so no rebuild is left running when a test file ends |
| `LISTING_DELAY_MS` | `0` | The least time before a listing index segment builds after a change (`ListingIndexer.apply`, `apps/catalog/src/listings.ts`), on top of the debounce (15 s, or a second per 20,000 members of the last build, at most 5 minutes). `0` builds a new category's index at once. The tests set it to an hour and run each build themselves (`runDurableObjectAlarm`), so no build is left running when a test file ends |
| `PUBLISH_FANOUT` | `32` | Publishers (`CatalogPublisher`) each shard spreads a pass's storage writes over (`apps/catalog/src/publisher.ts`, `publishKeys`). One invocation has only six storage calls in flight, so this multiplies how fast a shard publishes. A string; `32` when unset, `0` or not a number, and a negative value becomes 1. `1` makes the shard do its writes itself. Raising it creates more publisher objects (`pub-<shard>-<n>`); lowering it strands none, since publishers keep no state |

## Compatibility flags

`apps/engine/wrangler.jsonc` sets `nodejs_compat` and `global_fetch_strictly_public`. The second
makes the engine's outbound `fetch` (outbound webhooks, [A2A push
notifications](https://docs.commerceworker.com/reference/a2a/#push-notifications) and live shipping carriers' quote
requests, whose URLs callers or flow authors supply) reach public addresses only, not private or loopback ones.
On top of that platform rule, every server-side fetch of such a URL (those, UCP order webhooks,
images for a model step, and the web Worker's single sign-on discovery, token and key requests)
goes through `safeFetch` (`packages/core/src/egress.ts`): https only, no credentials in the URL,
no IP literals, internal names (`localhost`, `.internal`, `.local`, `.lan`, `home.arpa`, single
labels) or wildcard-DNS services (`nip.io`, `sslip.io`), no redirects (a model step's images may
follow three for a plain GET, each checked again), a timeout, and a byte cap on what is read.
Single sign-on discovery may follow two redirects; the token request follows none. A host ending
in a dot is refused. Outbound webhooks, A2A push and UCP order webhooks still allow plain http to
`localhost` for local development, and webhook subscriptions, A2A push configs and a UCP profile's
webhook are checked against the same policy when they're registered.

## Engine secrets

Set with `pnpm --filter @commerceworker/engine exec wrangler secret put <NAME>`.

| Secret | Meaning |
|---|---|
| `PRINCIPAL_KEY` | Required, at least 32 characters (the deploy refuses a shorter one, or a shorter `DATA_KEY` or previous key: `keysProblem` in `scripts/fleet.ts`). The key the engine checks the signature on the principal header with, the same value as the web Worker's. The engine refuses `/mcp`, `/a2a`, `/ucp/*` (whose header is a separate `u1` envelope, see [UCP](architecture.md#ucp-agentic-checkout)) and the agent sockets without a header signed with it (and logs that it is unset). Local dev needs nothing: `apps/web/vite.config.ts` gives the engine `DEV_PRINCIPAL_KEY` (from core). See [Rotating the principal key](operations.md#rotating-the-principal-key) |
| `PRINCIPAL_KEY_PREVIOUS` | Optional, only during a rotation: the old key, also accepted for verification. Remove it once the new key is deployed |
| `DATA_KEY` | Required. Encrypts the secrets the deployment stores (AES-256-GCM, key derived with HKDF-SHA256; `encryptSecret` in core): in this Worker the A2A push configs' `token` and `auth_credentials` and the queued notifications' `headers` in each `A2AAgent`'s SQLite, and the webhook and integration secrets it reads to sign deliveries. The same value as the web Worker's. Local dev needs nothing: `apps/web/vite.config.ts` gives the engine `DEV_DATA_KEY` (from core); the engine tests bind `DATA_KEY: 'test-data-key'`. See [Rotating the data key](operations.md#rotating-the-data-key) |
| `DATA_KEY_PREVIOUS` | Optional, only during a rotation: the old key, still read, and the daily sweep moves what it sealed onto `DATA_KEY` (`resealSecrets`, `apps/engine/src/data-key.ts`). Remove it once the sweep reports no unreadable secrets |
| `INTAKE_ALLOWLIST` | Extra senders allowed to start orders by email: addresses or `@domains`, comma-separated. Customers' own addresses and company domains are always allowed. See [Email intake](https://docs.commerceworker.com/guides/email-intake/#who-may-send) |
| `SHIPPING_CARRIER_AUTH` | Credentials for the live carriers in a [Shipping rate](https://docs.commerceworker.com/reference/nodes/#commerce.shipping_rate) node's `liveCarriers`: a JSON object from carrier `id` to the `Authorization` header value sent with its quote request, e.g. `{"acme":"Bearer …"}`. A carrier with no entry is called without one; unparseable JSON counts as empty. See [Shipping rates](https://docs.commerceworker.com/guides/fulfillment/#shipping-rates) |
| `UCP_SIGNING_KEY` | Optional. A private P-256 JWK (`kty` `EC`, `crv` `P-256`, `d`) with a `kid`, as JSON: the key that signs [UCP](https://docs.commerceworker.com/reference/ucp/#orders-and-events) order events (RFC 9421, ES256). Its public half is published in `keys` at `/.well-known/ucp`. Without one (or if it doesn't parse, which is logged) the profile publishes no keys and no order events are sent, since UCP requires them signed. Generate one with `crypto.subtle.generateKey({ name: 'ECDSA', namedCurve: 'P-256' }, true, ['sign'])` and `exportKey('jwk')`, add a `kid`, and add it to the deployment's GitHub environment secrets; the deploy passes it to the engine. Tests use a throwaway key in `apps/engine/vitest.config.ts` |
| `STRIPE_SECRET_KEY` | Stripe secret or restricted key (`sk_…`, `rk_…`), required when `PAYMENTS_MODE` is `stripe`. A restricted key needs write access to PaymentIntents, Refunds and Customers, and to Invoices and Invoice Items when a flow issues invoices through Stripe. With a test key (`sk_test_`/`rk_test_`), an order with no payment method pays with `pm_card_visa`, and `meta.simulate` `payment_decline` or `charge_fail` uses `pm_card_visa_chargeDeclined`; a live key never substitutes a card. Every request pins `Stripe-Version` (`STRIPE_API_VERSION` in `apps/engine/src/stripe.ts`). Deploys pass it from the deployment's GitHub environment (`SECRETS` in `scripts/fleet.ts`) |

## Storefront variables and secrets

`apps/storefront/wrangler.jsonc` has one variable, `TURNSTILE_SITE_KEY` (the web Worker's, rendered from the same
registry `turnstileSiteKey`, empty without one; the sign-in form's challenge, `app/lib/turnstile.server.ts`), and no
`PRINCIPAL_KEY`: the storefront is public, so a compromise of it must not be able to sign as staff. Its secrets are
`TURNSTILE_SECRET_KEY` (the same widget's, set by `fleet.ts secrets storefront` when the environment has it; a
deployment with a site key can't deploy without it) and `STOREFRONT_KEY`, the HMAC-SHA256 of
`PRINCIPAL_KEY` over the label `commerceworker-storefront` (`storefrontKey` in `packages/core/src/roles.ts`, mirrored
in `scripts/fleet.ts`; the engine derives the same from its own `PRINCIPAL_KEY`). It signs the envelopes the
storefront forwards to the engine (a cart's buyer, `signCartGuest`; a UCP platform, `signPlatform`; a buyer on
one call, `signGuestActor`) and the cookie a start link sets (`signCartGuestSession`). `STOREFRONT_KEY_PREVIOUS`,
derived from `PRINCIPAL_KEY_PREVIOUS`, verifies that cookie during a rotation, and is written only when that is set.
`fleet.ts secrets storefront` derives both from the deployment's environment; the principal key itself is never
written to the Worker. The engine takes these envelopes under the storefront key alone, and v1 principals and
staff actors under `PRINCIPAL_KEY` alone. A platform's API key and a buyer's cookie never leave this Worker; the engine
gets only the signed envelope (and a platform key's hash). In local dev the key is derived from `DEV_PRINCIPAL_KEY`.

## Web secrets

Set with `pnpm --filter @commerceworker/web exec wrangler secret put <NAME>`, or in `apps/web/.dev.vars`
for local dev (copy `apps/web/.dev.vars.example`).

| Secret | Meaning |
|---|---|
| `PRINCIPAL_KEY` | Required. Signs the principal header on every request the web Worker forwards to the engine (order and assistant sockets, `/mcp`, `/a2a`, `/ucp/*`): HMAC-SHA256 over the principal, the path and a 60-second expiry (`signPrincipal`, `apps/web/app/lib/principal.server.ts`). Must equal the engine's. In local dev it falls back to `DEV_PRINCIPAL_KEY`; elsewhere an unset key fails the request. `scripts/provision.sh` generates it (`openssl rand -hex 32`); a deploy fails before migrating when the GitHub environment lacks it |
| `DATA_KEY` | Required. Encrypts the secrets the web app stores in D1: `users.totp_secret`, `integrations.secret` and `previous_secret`, `webhook_subscriptions.secret` and `previous_secret` (`sealSecret` and `openSecret`, `apps/web/app/lib/data-key.server.ts`). Must equal the engine's. In local dev it falls back to `DEV_DATA_KEY`; elsewhere an unset key throws. `scripts/provision.sh` generates it (`openssl rand -hex 32`) beside `PRINCIPAL_KEY`; a deploy fails before migrating when the GitHub environment lacks it. Never lose it: see [Rotating the data key](operations.md#rotating-the-data-key) |
| `DATA_KEY_PREVIOUS` | Optional, only during a rotation: the old key, still read. Remove it once the engine's sweep has moved every secret onto `DATA_KEY` |
| `PASSWORD_PEPPER` | Optional, recommended (`scripts/provision.sh` makes one, 64 hex digits; the deploy refuses one under 32 characters). Mixed into every password hash: PBKDF2 runs over HMAC-SHA256(pepper, password), stored as `pbkdf2p:<pepper id>:…`, so a copy of D1 alone can't be cracked. The pepper id is 8 characters of an HMAC under the pepper of a fixed label: it names which pepper made a hash without revealing it. A hash from before it was set (`pbkdf2:…`) still verifies and is stored again with it at that person's next sign-in. **Never change or remove it once set**: every peppered password would stop verifying, and people would need an admin to reset theirs. If it happens, sign-ins fail as `auth.sign_in_failed` with reason `password pepper mismatch` and the web Worker logs `password_pepper_mismatch`; restoring the old value fixes it |
| `SETUP_TOKEN` | The deployment's one-time setup code: on `/setup` it creates an admin account, once (its SHA-256 is recorded in `workspace_settings` as `setup_code_used`). `scripts/provision.sh` generates it into `.secrets/<id>/setup-code` and `scripts/setup-code.sh` replaces it to recover admin access. Unset, `/setup` creates nobody. See [Sign-in setup and open mode](deploy.md#sign-in-setup-and-open-mode) |
| `OIDC_CLIENT_SECRET` | The identity provider's client secret for single sign-on, from the deployment's GitHub environment (`deploy.yml` passes it; `fleet.ts` lists it among the web Worker's secrets). ## Content stack secrets

A deployment with `"content": true` ([Operations](operations.md#the-content-stack)) deploys the content Workers with these secrets, set in the same GitHub environment as the commerce ones; `node scripts/fleet.ts secrets <pipeline|media|api|delivery|studio> <out> <id>` writes each Worker's only (`CONTENT_SECRETS` in `scripts/fleet.ts`), refusing a deployment with content off, a missing required secret, or a key under 32 characters.

| Secret | Worker | Meaning |
|---|---|---|
| `PRINCIPAL_KEY`, `PRINCIPAL_KEY_PREVIOUS` | studio, api | The same key as the commerce web Worker's. The studio signs the principal header it forwards to the api and the api verifies it. The pipeline and delivery never hold it |
| `ASSISTANT_PRINCIPAL_KEY`, `ASSISTANT_PRINCIPAL_KEY_PREVIOUS` | pipeline | Not in the environment: derived at each deploy from `PRINCIPAL_KEY` (and the previous one) with HKDF (`scripts/derive-assistant-key.ts`, the same salt and info as `deriveAssistantPrincipalKey` in `packages/security`), so a principal the pipeline could forge is good for the assistant's socket and nothing else |
| `DATA_KEY`, `DATA_KEY_PREVIOUS` | studio, api, pipeline, delivery | Seals the secrets the content stack stores in its own database. The same value as the commerce Workers'; rotate it the same way ([Rotating the data key](operations.md#rotating-the-data-key)) |
| `TOKEN_PEPPER` | api, pipeline, delivery | Required with content. In every API key hash: never change it once a deployment runs. `scripts/provision.sh` generates it, and refuses to when the api already holds one the environment lost |
| `MEDIA_SIGNING_SECRET` | api, pipeline, delivery, media | Required with content. Signs the `/media/*` URLs the api and delivery hand out and the media Worker verifies. Changing it invalidates URLs already handed out |
| `PASSWORD_PEPPER`, `SETUP_TOKEN`, `OIDC_CLIENT_SECRET` | studio | The same as the commerce web Worker's: the studio's password hashes use the same pepper, its `/setup` takes the same one-time code (redeemed once in each database), and single sign-on uses the deployment's `sso` entry with a second redirect URI (`https://<studioDomain>/login/sso/callback`) |
| `STREAM_WEBHOOK_SECRET`, `MCP_TOKEN`, `ADMIN_TOKEN` | api | Optional: the Stream webhook's signing secret, and the static MCP and admin tokens |

The content Workers' bindings and variables are in each app's `wrangler.jsonc` (`apps/pipeline`, `apps/api`, `apps/media`, `apps/studio`, and `apps/delivery`'s content template); `scripts/fleet.ts` renders them per deployment: the content database (`commerceworker-content<suffix>`) as `DB` on every one of them, `KV_CACHE`, `MEDIA_BUCKET`, `VECTORIZE`, the queues, Workflows and Durable Object script names (`commerceworker-pipeline<suffix>`) with the deployment's names, `MEDIA_BASE_URL` (the api's host), `MEDIA_PUBLIC_URL` (the media host), `OAUTH_ISSUER` (the studio's host), `QUEUE_SUFFIX`, `AI_GATEWAY_ID` and `DATA_JURISDICTION`. Their rate-limit namespaces are `<slot>501` to `<slot>506`.

## Alert secrets

Not Worker secrets: inputs to `./scripts/provision.sh <id>`, exported in the shell that runs it, and used only when the deployment's registry sets `redundancy.alerts` ([Alerting](operations.md#alerting)). Neither is printed or written to disk.

| Variable | Notes |
|---|---|
| `ALERT_WEBHOOK_URL` | The webhook the notification policies and Health Checks post to (a chat or incident tool's incoming URL, or your own endpoint). Becomes the destination `commerceworker-alerts<suffix>`, updated in place when the script runs again. Unset, the registry's `alerts.webhook` is used if it has one |
| `ALERT_EMAIL` | Optional: an address the policies also email |

PagerDuty has no secret here: it is connected to the account in the dashboard (Notifications > Destinations > PagerDuty), and `alerts.pagerduty` in the registry says to send to it.

| `API_LIMIT`, `AGENT_LIMIT`, `WEBHOOK_LIMIT` | web | Per-caller budgets (`app/lib/rate-limit.ts`): 600 requests a minute per principal on `/api/v1` (after authentication), 300 per principal on each of `/mcp` and `/a2a` (keyed `<path>:<principal id>`) and 300 per registered UCP platform on `/ucp` (`/ucp:<platform id>`, `AGENT_LIMIT`), and 1,200 per integration on the signed webhooks (after the signature verifies, so a forged request can't spend a sender's budget) or per shop on Shopify's. Over the limit answers `429` with `Retry-After: 60`. A deployment's `limits` in the registry replace these numbers ([Operations](operations.md#the-registry)). Counted per Cloudflare location, so they stop a runaway client rather than meter it exactly. Without the binding (unit tests) nothing is limited |
| `TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY` | storefront | The same widget as the web Worker's (`turnstileSiteKey` in the registry renders the var, always set and empty without one; the secret is the environment's `TURNSTILE_SECRET_KEY`, which `fleet.ts secrets storefront` writes beside `STOREFRONT_KEY`, and a deploy stops without it). With a site key, Pay on a hosted checkout asks for a challenge for action `checkout_pay` and checks it (`checkPayTurnstile`, `app/lib/turnstile.server.ts`) before the engine is asked anything; `400` for no token, `403` for a failed or wrong-action or wrong-host one, `503` for Siteverify unreachable or a key with no secret. Only a checkout page that takes a card adds Turnstile to its policy. Empty: no challenge |
| `APPLE_PAY_DOMAIN_ASSOCIATION` | engine | Secret (public text, kept a secret only for where a deploy reads it from): the contents of Stripe's Apple Pay domain verification file for the storefront's host. The storefront serves it at `/.well-known/apple-developer-merchantid-domain-association` as `text/plain` (`StorefrontRpc.applePayDomainAssociation`, held five minutes per isolate), and answers `404` without it. How the owner gets it: [operations](operations.md#card-payment-on-the-hosted-checkout) |
| `stripePublishableKey` (registry) | fleet | With it the storefront's hosted checkout takes cards, so `scripts/fleet.ts` refuses it without a `turnstileSiteKey` |
| `PAY_LIMIT` | storefront | 10 card payments a minute on a hosted checkout, counted twice per press: per cookie (`pay:<cookie budget key>`) and per client address (`pay:ip:<cf-connecting-ip>`), before Turnstile or the engine; its own namespace (`<slot>010`), not set by the registry's `limits`. The session's own cap, `HOSTED_PAY_ATTEMPTS` (5 attempts with a card, counted when a payment is claimed), is the third guard against card testing |
| `PROMO_LIMIT` | storefront | 20 changes to a hosted checkout's promo codes a minute per cookie (`promo:<cookie budget key>`), on top of `API_LIMIT`; its own namespace (`<slot>008`), not set by the registry's `limits` |
| `SIGNIN_EMAIL_LIMIT`, `SIGNIN_IP_LIMIT` | storefront | A shopper's sign-in, asking for a code and trying one: 10 a minute per email address (an HMAC of it under `STOREFRONT_KEY`, `start:`, `code:` and `link:` kept apart) and 20 per client address, in their own namespaces (`<slot>011` and `<slot>012`), not set by the registry's `limits`. Over the limit the page says to wait a minute (`429`, `Retry-After`) |
| `API_LIMIT`, `AGENT_LIMIT`, `CATALOG_LIMIT` | storefront | The storefront's own budgets (`app/lib/rate-limit.ts`), in their own rate-limit namespaces (`<slot>006`, `<slot>007` and `<slot>009`; `PROMO_LIMIT`, above, is `<slot>008`, and `PAY_LIMIT` is `<slot>010`) and set by the same registry `limits` keys as the web Worker's (`api`, `agents`, `catalog`): 600 requests a minute per cart and buyer on product search (`cart-search:<cartId>:<buyer id>`), 300 per registered UCP platform on `/ucp` (`/ucp:<platform id>`, `AGENT_LIMIT`) and, apart from that, 120 per platform on its catalog search and lookup (`/ucp/catalog:<platform id>`, `CATALOG_LIMIT`): the REST paths `/ucp/v1/catalog/*` and an MCP `tools/call` of `search_catalog`, `lookup_catalog` or `get_product`. second keeps fetches of an MCP client's Client ID Metadata Document (an https `client_id`) to the

## Routes and hostnames

The web Worker serves `app.commerceworker.com` as a custom domain; change `routes` in
`apps/web/wrangler.jsonc` for your own. The engine has no routes, no `workers.dev` URL and no preview
URLs: only the web app's service binding reaches it, plus Email Routing rules that send mail to it
(see [Email intake](deploy.md#email-intake)). The docs Worker (`apps/docs/wrangler.jsonc`)
serves `docs.commerceworker.com`, and likewise sets `workers_dev` and `preview_urls` to `false`.

The storefront Worker serves `shop.commerceworker.com` as a custom domain (a customer's is the registry's
`storefrontDomain`, default `shop.<domain>`, rendered at deploy), with `workers_dev` and `preview_urls` off,
like the web app: the buyer's pages, their cart's files, product search and socket, and UCP. It is uncached
(no Workers Caching; an HTML page without its own `cache-control` gets `private, no-cache`) and has no
sign-in. It answers `GET /health` with `{ ok: true, service }` and `GET /health/deep` with the checks of its
D1, R2 and the engine. Its compatibility flag is `nodejs_compat`; `observability` is on at sampling 1, as
the web app's, and `limits.cpu_ms` is 5,000.

The catalog Worker has no routes, no `workers_dev` URL and no preview URLs, and only delivery
(`SearchApi`) and the web app (`CatalogApi`) bind to it; it answers `GET /health` with `{ ok: true }` and `404` otherwise. CI doesn't smoke-test it.

The delivery Worker serves `catalog.commerceworker.com` as a custom domain (a customer's is the
registry's `catalogDomain`, default `catalog.<domain>`, rendered at deploy), with `workers_dev` and
`preview_urls` off. It answers `GET /health` with `{ ok: true, serves: ["catalog"] }` (it names only the surfaces that are bound; content is off here), and CI smoke-tests it. Its
compatibility flags are `nodejs_compat` and `global_fetch_strictly_public`; `observability` is on
with `head_sampling_rate` 0.05 (logs from 5% of requests; every request is still counted in Analytics
Engine) and source maps are uploaded.

With the content stack, the studio serves `studio.<domain>`, the api `api.<domain>`, the media Worker `media.<domain>` and delivery also `cdn.<domain>` (the registry's `studioDomain`, `apiDomain`, `mediaDomain` and `cdnDomain`, only with `content: true`), each a custom domain with `workers_dev` and `preview_urls` off; the pipeline has no route. Delivery then deploys its dispatcher entry and answers `GET /health` with `serves: ["catalog", "content"]` on either host. All of them send trace events to Logpush.

The web, storefront and engine Workers answer `GET /health` with `{ ok: true, service }`. The web app's
`GET /health/deep` also checks D1, R2 and the engine, and `POST /health/write`, which only CI can
sign, writes through every store (see [Request routing](architecture.md#request-routing)). The web app sets `workers_dev` and
`preview_urls` to `false` too, so `app.commerceworker.com` is its only address and the zone's rules apply to
every request.

## Runtime limits and observability

The catalog Worker turns `observability` on at the default sampling and sets `limits.cpu_ms` to 300,000, since a feed step parses and validates up to 25,000 products. The web, storefront and engine Workers log and trace every request (`observability` with `head_sampling_rate` 1, invocation logs
and traces on); lower the rate once traffic makes the volume or cost matter. All five (web, storefront, engine,
catalog, delivery) turn on Workers Issues (`observability.issues.enabled`), which groups
uncaught exceptions, failed invocations, `5xx` responses and error-level logs into issues and is
what the account's alerting watches; see [Alerting](operations.md#alerting). All five also set
`observability.redact_query_string`, so OAuth codes and states and other query strings stay out of
logs and traces. Each Workflow (`commerceworker-order`, `commerceworker-replenish`, `commerceworker-d1-backup`, `commerceworker-d1-restore`, `commerceworker-catalog-feed`,
`commerceworker-catalog-backup`, `commerceworker-catalog-restore`)
sets `default_retention`: finished instances are kept 7 days, errored ones 30, the most Workflows
keeps. `limits.cpu_ms` stops a
runaway invocation: 5,000 for the web app and the storefront, 10,000 for the engine (the platform default is 30,000). I/O
waits, such as model calls, don't count against it. The web, storefront and engine Workers set `placement.mode` to `smart`: the web
app runs near D1 and the engine, and the storefront near the engine, rather than near the visitor, and the engine runs near D1 rather
than near the web app (keep it only while Observability shows lower D1 latency).

All five, and every plugin Worker (`renderPlugin` sets it), set `logpush: true`: their trace
events go to Workers Logpush too, whose per-deployment job (`commerceworker-workers<suffix>`, made by
`provision.sh`) keeps them in the logs bucket `commerceworker-logs<suffix>` for `logRetentionDays`.
A deploy never waits on the job. Without it the logs are kept nowhere of ours, but another
unfiltered `workers_trace_events` job on a shared account would still collect them;
`provision.sh` refuses to run while one exists. What is kept, what is
left out and how to read it: [Logs](operations.md#logs).

Each audit write logs one JSON line, `{"type":"audit_event", …}` with the sealed row, to Workers Logs, and through Logpush to the logs bucket; a failed write logs `{"type":"audit_write_failed","action":…,"error":…}` instead, to alert on. Writing still never throws.
