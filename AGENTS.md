# AGENTS.md

CommerceWorker is API-first, agent-first commerce infrastructure on Cloudflare; every order runs as an Order Flow (the `OrderWorkflow` Workflow). It's a pnpm + Turborepo + Biome monorepo; read README.md for the architecture, `docs/port-map.md` for where each part came from, and `PRODUCT.md` / `docs/brand/` for voice.

## Layout

One platform, one product (CommerceWorker). Commerce and content run side by side today and converge phase by phase (ROADMAP).

| App | Role |
|---|---|
| `apps/web` | Commerce admin and REST API (React Router on Workers): flows, orders, approvals, catalog, team |
| `apps/engine` | Order Flows: the `OrderWorkflow` Workflow, OrderAgent, CartAgent, AssistantAgent, UCP, A2A, MCP, plugins |
| `apps/catalog` | Sharded product catalog |
| `apps/studio` | Content admin (React Router 8 SSR) and human auth; fronts `apps/api` with a signed principal |
| `apps/api` | Content Management and Preview REST, MCP, OAuth, live (Hono, from `packages/http`) |
| `apps/delivery` | Public delivery: content (uncached gateway in front of a cached `Delivery` entrypoint) and the catalog's read-only edge (`CatalogDelivery`, at `catalog.<host>`), each off unless its bindings are bound |
| `apps/media` | The optional assets service at `media.<host>` |
| `apps/pipeline` | Content queue consumers, cron, Durable Objects and Workflows (no route) |
| `apps/docs` | The one public docs site (Starlight): commerce at the root, content management under `/content/` |
| `apps/marketing` | commerceworker.com: static Astro pages in English and Spanish, served as Workers static assets |

| Package | Role |
|---|---|
| `packages/core` | Commerce domain with no bindings: flows, planner, catalog, pricing, checkout, UCP, plugin contract |
| `packages/db` | Commerce D1 schema (Drizzle) and migrations |
| `packages/domain`, `ports`, `application` | The hexagonal core: pure domain, port interfaces, use-cases |
| `packages/store` | The D1 store behind the ports, with its hand-written migrations |
| `packages/adapters`, `platform` | Cloudflare adapters (one subpath each) and the composition root (`wire.ts`) |
| `packages/http` | The Hono surface as a library: REST routes, OpenAPI, MCP tools and skills |
| `packages/design`, `ui` | Ledger tokens (held to both admins' `app.css`) and the shared components |
| `packages/sdk/*`, `cli` | The public SDK and the `commerceworker` command |
| `packages/i18n`, `guardrails`, `media-upload-limits` | Locale resolution and i18next setup; AI input and output guardrails (PII, prompt injection, regex); upload limits |
| `packages/plugin-sdk`, `security`, `redaction`, `telemetry`, `test-kit`, `seed`, `agent-runtime`, `graphql-gen`, `docs-index` | Supporting packages |

## Commands

```bash
pnpm install
pnpm web:dev                 # web, engine and catalog together (engine and catalog are Vite auxiliary Workers)
pnpm test                    # turbo → vitest (core in node, engine and catalog e2e in workerd, web in node)
pnpm lint                    # turbo → biome check
pnpm check-types             # turbo → tsc --noEmit (web runs react-router typegen first)
pnpm test:fleet              # deployments/ registry and the configs scripts/fleet.ts renders
pnpm test:toolkit            # .claude/ toolkit: skill/agent lint and hook tests (see .claude/README.md)
pnpm commitlint --from origin/main  # commit messages since main: Conventional Commits, `type(scope): subject`
pnpm --filter @commerceworker/<pkg> test     # one package's tests
pnpm --filter @commerceworker/web e2e        # device tests: WebKit as iPhone, iPad and desktop (offline dev server; E2E_PORT=… beside another worktree)
pnpm turbo run lint check-types test --filter='...[origin/main]'  # what changed since main, plus dependents
pnpm --filter @commerceworker/engine types   # after changing apps/engine/wrangler.jsonc
pnpm --filter @commerceworker/web types      # after changing apps/web/wrangler.jsonc
pnpm --filter @commerceworker/catalog types  # after changing apps/catalog/wrangler.jsonc
pnpm plugin:check <deployment> <plugin>      # before removing a plugin (needs COMMERCEWORKER_API_TOKEN)
pnpm catalog:bench <deployment> [products]   # time a deployed catalog end to end, then delete (needs COMMERCEWORKER_API_TOKEN)
pnpm docs:dev / docs:build              # Starlight docs in apps/docs (build includes a link check)
pnpm sync:theme                         # regenerate the docs theme from packages/design tokens
pnpm --filter @commerceworker/marketing dev   # commerceworker.com (build: link check; test: copy parity across locales)
```

## Rules

- **Cloudflare primitives first.** Use a Cloudflare product wherever one fits: D1 and Durable Object SQLite for data, Workflows for durable processes, Queues for async fan-out, R2 for documents, KV for edge reads, Workers Caching for delivery, Workers AI through AI Gateway for models, Email Routing and Email Sending for mail, Worker Loader for sandboxed code, and Secrets Store for credentials. A third-party service needs a reason the platform can't meet, written in the PR.
- **No Neon, no Postgres, no Hyperdrive.** D1 is the system of record. Logic ported from Commerce Worker v1 (Drizzle on Neon) is re-implemented against D1, never with its driver.
- **Converging on a hexagonal layout.** The platform packages are that layout: `packages/domain` → `ports` → `application`, adapters in `packages/adapters`, the D1 store in `packages/store`, bound only at composition roots (`packages/platform`'s `wire.ts` and the app entries), served over REST and MCP by `packages/http`. The commerce engine (`packages/core`, `apps/engine`, `apps/web`) moves onto it phase by phase (ROADMAP). New commerce code follows the pricing slice, the pattern every connector area moves to: domain rules in `packages/core`; a port in `packages/ports/src/commerce/` (plain records, no ORM types); a D1 adapter in `packages/db` (its own subpath, e.g. `@commerceworker/db/pricing-store`); an in-memory store and a contract suite in `packages/test-kit/src/commerce/`, the contract run against both (test-kit in node, `packages/db/test` in workerd); use-cases in `packages/application/src/commerce/` that take the ports and `now` as arguments; and the engine binds adapters only in `apps/engine/src/wire.ts`, the one engine file that imports `@commerceworker/db` or uses `env.DB`; the web app binds them only in `apps/web/app/lib/wire.server.ts`, the one web file that imports `@commerceworker/db`, calls `createDb` or uses `env.DB`, and its tests swap a port for the test kit's in-memory store (`scripts/composition-root.test.ts` holds both). Never into a Durable Object or a 1,000-line connector. Path rules in `.claude/rules/` apply to the platform apps and packages; the content stack's own rules are in `docs/content/AGENTS.md`.
- **Every pattern that applies is merged.** `docs/patterns.md` lists each architectural pattern with its state (merged, partial, to merge). A change that adopts one updates its row, and a new capability follows the stricter of the two.
- **Every dependency version lives in the pnpm catalog** (`pnpm-workspace.yaml`, `catalogMode: strict`). A `package.json` names an external dependency `"catalog:"` and our own `"workspace:*"`, never a version; only `peerDependencies` keep their own ranges. Add a new dependency to the catalog first. `scripts/catalog.test.ts` fails CI on a stray version or an unused entry.
- **TypeScript is strict** (`packages/typescript-config/base.json`): `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, `noUnusedLocals`, `noUnusedParameters`. Use `import type` for types.
- **D1 limits are design inputs:** at most 100 bound parameters per statement, one writer per database (no per-request writes on read paths), 10 GB per database (append-heavy data goes to R2, derived indexes to Durable Objects). Statement counts per request are snapshotted (`packages/store/test/query-counts.json` for content, `packages/db/test/query-counts.json` for commerce): read paths may only go down, and a PR that raises one says why.
- Test files are named for the capability under test, never for a roadmap phase.
- Biome reads only an `.astro` file's frontmatter, so `biome.json` turns its unused-import and unused-variable rules off for `.astro` files; `astro sync && tsc --noEmit` still catches what's really unused. Don't add `biome-ignore` comments for them.
- The marketing site's copy (`apps/marketing/src/i18n/`) claims only what the product does today, in the voice of `docs/brand/messaging.md`; `es.ts` carries every key of `en.ts` (a test holds them together). Pricing and legal pages aren't published until pricing is decided and counsel supplies the text (`docs/brand/legal-outline.md`).
- **Brand vocabulary.** The product is CommerceWorker (one word) in copy and `commerceworker` in code. The order engine this started from is never named in the repo, like the platform's own sources; its Workflow is the `OrderWorkflow` class (binding `ORDER_WORKFLOW`) and the capability is "Order Flows". Never name a competing commerce platform; say "the surveyed platform". Don't use third-party commerce vocabulary in errors, permissions or headers.
- Never use a trailing "z" in endpoint names (`/health`, not `/healthz`).
- Production deploys from CI: merging to `main` runs `.github/workflows/ci.yml` (migrate D1, catalog, delivery, engine, web, docs). Don't deploy or run remote migrations by hand; if the deploy job fails, re-run its failed jobs.
- `packages/core` has no bindings and no Cloudflare imports. Anything that needs `env` belongs in an app.
- Planner semantics (readiness, skips, loops) live only in `packages/core/src/graph.ts` and are unit tested there. The Workflow adds durability; it must not re-implement scheduling.
- Workflow determinism: every effect happens inside a `step.do`, and anything that touches time or a model also goes in a step. Nodes are applied in graph order after each batch. Step names are `${nodeId}#${run}`; never rename them in a way that would change a published flow's names.
- Reports from the Workflow to the OrderAgent are either sequenced plan snapshots (non-durable; the agent drops stale ones) or detail reports sent from inside steps. Keep agent updates idempotent.
- Every connector write is keyed by its step key, and every compensation is idempotent. A node type with `rollback: true` in the catalog must have an entry in `ROLLBACKS` (`apps/engine/src/nodes.ts`).
- Adding a node type: add it to the catalog (`packages/core/src/catalog.ts`), add an executor (or interpreter case), and add its icon to `apps/web/app/components/node-icon.tsx`.
- `packages/db/src/schema.ts` must match `packages/db/migrations/*.sql`. Add a new numbered migration; never edit an applied one. CI applies migrations before it deploys the Workers, and a failed smoke test rolls the Workers back but not D1, so a migration must work with the code already deployed: add first (expand), and drop or rename only in a later change once nothing deployed uses it (contract).
- The web app talks to the engine only through `EngineRpc` (`packages/core/src/api.ts`) the proxied `/agents/order-agent/:id`, `/agents/cart-agent/:id` and `/agents/assistant-agent/*` sockets, and `/mcp` and `/a2a`, which it forwards after resolving the caller (`apps/web/app/lib/oauth.server.ts`), and `/ucp/*`, which it forwards after resolving the UCP platform (`apps/web/app/lib/ucp.server.ts`). The engine trusts the principal header on all of them only when it is signed with `PRINCIPAL_KEY` for that path and unexpired (`signPrincipal` and `verifyPrincipal` in `packages/core/src/roles.ts`); credentials never reach it. A UCP platform is signed as its own envelope (`signPlatform` / `verifyPlatform`) that no other route accepts, and acts only on the checkouts and orders it started. An external cart's buyer (admitted by a one-time start link, `apps/web/app/lib/cart-guest.server.ts`) is signed as a cart guest (`signCartGuest` / `verifyCartGuest`) that only that cart's socket accepts. Each of `/mcp` and `/a2a` is its own OAuth resource: a token works only at the endpoint it was granted for. The web app never imports engine source.
- Agentic checkout (UCP, `apps/engine/src/ucp/`) prices a session with the checkout flow's own pricing nodes (`quoteNodes` in `packages/core/src/checkout.ts`), so the PaymentIntent it holds at completion is the amount the flow's authorize node adopts. Don't price checkouts any other way. What it serves is tested against UCP's published schemas (`packages/core/tests/fixtures/ucp`, vendored unchanged).
- Visual design is "Ledger": shadcn's base-maia preset (neutral greys, Inter, pill buttons and fields) on the Radix primitives in `packages/ui`, with the status tokens (`ok`, `wait`, `bad`, …) kept (tokens in `apps/web/app/app.css`). Don't reuse styling from other projects. `packages/design/src/tokens.ts` mirrors those tokens (its tests fail if they differ) and generates the docs theme: after changing a token in `app.css`, change it there and run `pnpm sync:theme`. The docs' design is recorded in `apps/docs/DESIGN.md`.
- The web app works on iPhone and iPad, in Safari and installed to the Home Screen. Pad for the notch, status bar and home indicator with the `pt-/pb-/px-safe-*` utilities (insets are `--safe-*`, never `env()` directly); size full-height layouts with `--shell-h` and `--tabbar-h`; give a small control `hit-area` (44px on touch) rather than growing it; show keyboard hints only with `fine:`; never set a field's font below 16px on touch (app.css enforces it). Below lg the flow editor is review-only and an order's graph is its own tab. Check layout changes with `pnpm --filter @commerceworker/web e2e`.
- The product catalog (`apps/catalog`, model in `packages/core/src/product/`): the shard hash and counts (`routing.ts`) are frozen by golden tests, since changing them strands every stored product; never update those expected values. Product types change only by a new, additive version (`typeChangeIssues`). A change to a published document's shape bumps `DOC_FORMAT` and needs a reindex. A write lands in the shard's transaction with its outbox row and publishes from the alarm; never publish outside the outbox. Shards never await another shard while holding a transaction or `blockConcurrencyWhile` (two shards claiming aliases from each other would deadlock). Callers type the catalog binding as `ProductCatalogRpc`, as the web app does with `EngineRpc`; a new catalog resource goes in `scripts/fleet.ts` and `scripts/provision.sh` so every deployment gets its own. The catalog entrypoint of `apps/delivery` (`src/catalog/`, deployed from `wrangler.catalog.jsonc` with its own entry, `src/catalog/worker.ts`, so no content code ships) is read-only and serves only what the publisher wrote; it imports core only through the zod-free subpaths `@commerceworker/core/product/paths`, `@commerceworker/core/product/listing` and `@commerceworker/core/product/search` (types may come from `@commerceworker/core/product`), imports nothing of the content stack, and keeps its bundle at ~10 KiB gzipped (`test/catalog-bundle.test.ts` holds both), and every request reaches its cached `CatalogDelivery` entrypoint by its canonical URL (`src/catalog/routes.ts`). Purges are rationed (Workers Caching uses Free-plan limits): freshness comes from `max-age` and ETag revalidation, and only urgent writes queue a purge.
- Plugins (`plugins/<id>/`, contract in `packages/core/src/plugins.ts`, see `docs/plugins.md`) are optional Workers a deployment installs through its registry's `plugins`, bound as `PLUGIN_<ID>`. A plugin imports only `@commerceworker/core`, `@commerceworker/design` and `@commerceworker/plugin-sdk`, is built with `definePlugin` and passes `pluginContract` in its own tests, gets buyer details only if its manifest sets `personalData: 'send'` and the deployment's registry grants it (`plugins.<id>.personalData`), reads credentials only from the `secrets` its manifest declares (set per deployment as `PLUGIN_<ID>_<NAME>`, in its GitHub environment or, on its own Cloudflare account, its Secrets Store) through `secret()`, and its database through `pluginDb()`, keeps its manifest in `src/manifest.ts`, holds only its own `PLUGIN_KEY` (derived from `PRINCIPAL_KEY`, never the key itself), serves pages that run no script (HTML, or a view the web app draws in its own shell: `viewResponse`, checked by `checkPluginView`), owns its own D1 database and migrations (the core schema never holds a plugin's tables), namespaces its node types `<id>.<name>`, and keys every write and compensation by order id + step key and every delivery by its payload id. A plugin asks the core for anything only through its `COMMERCEWORKER` binding (`PluginHostRpc`, served by `PluginHost` in `apps/engine/src/plugin-api.ts`), as itself (the binding's props, never an argument), and only with a capability its manifest declares and the registry grants (`plugins.<id>.capabilities`; a runtime install never gets one). The assistant drafts only logic plugins (`apps/engine/src/assistant/plugin-draft.ts`): the engine writes the manifest and host module (no egress, secrets, buyer details or storage), the model writes only rule bodies and test cases, and a draft is approved only with a case for every step passing and `pluginInstalls.assistant` on. The core never imports plugin code and must keep working with no plugin bound: the engine's default test project runs without one. A plugin may also be the provider behind a built-in node (manifest `provides`; the node keeps its contract and the engine applies what the provider returns; see "Providers" in docs/plugins.md). A deployment runs a plugin as its own Worker (`runtime: worker`) or sandboxed in the engine (`runtime: sandboxed`: a pinned bundle loaded by Worker Loader with capabilities only, egress through the engine's gateway, which injects its credentials, and per-call limits; `apps/engine/src/plugin-host.ts`). Never give a sandboxed plugin a binding, or let a plugin's text reach the timeline without `scrubCredentials`. `plugins/example` and `plugins/fixture-carrier` are test fixtures that no deployment may install. An admin installs a sandboxed plugin at runtime only from a `.cwplugin` signed by a publisher in the registry's `pluginInstalls` (`apps/engine/src/plugin-installs.ts`); a registry plugin wins on its id, approving, rolling back and uninstalling need a step-up (`stepUp`; for single sign-on only, signing in again at the provider, `auth_time` checked), and secrets an admin enters are sealed in `plugin_secrets` and never returned.
- Every workerd test project sets `fsModuleCache: false`: the Workers pool shares one module cache under `node_modules/.vitest-cache`, and parallel suites read files another is rewriting. A new workerd suite sets it too.
- Docs: `apps/docs` (Starlight, published) is for workspace users and integrators; how CommerceWorker is built, configured, deployed and tested lives in `docs/` (Markdown, unpublished). Keep source paths, env vars, bindings and `wrangler` out of the site. When a change touches a documented surface, update the docs in the same change: follow the `docs-sync` skill or delegate to the `docs-sync` agent. The source→page map is `.claude/skills/docs-sync/references/surface-map.tsv`. Content management pages live under `/content/` (`src/content/content/`, components in `src/components/content/`). Reference pages render from `@commerceworker/core` and `@commerceworker/domain` at build time, and the two OpenAPI explorers from `apps/web/app/lib/openapi.ts` (`/api/`) and the content API's generated document (`scripts/content-openapi.ts`, `/content/api/`); never hand-copy catalog data or enums into MDX. The docs import only those packages and `@commerceworker/http` (for the generator), never engine source.
- `@callable()` uses TC39 decorators; `apps/web/vite.config.ts` and `apps/engine/vitest.config.ts` include `agents/vite` so they are transformed (the engine has no Vite config of its own; in dev it runs inside the web app's Vite session).

# This is NOT the Turborepo you know

Turborepo configuration, task behavior, and CLI commands can vary between installed versions and may differ from your training data. Resolve the `turbo` package from this file's directory or relevant workspace; in monorepos, it may not be visible from the repository root. For example, run `node -p "require.resolve('turbo/package.json')"` from a workspace that depends on `turbo`.

Read `docs/README.md` inside that installed package first, then read the relevant pages from its `docs/` directory before changing Turborepo configuration or commands. Heed deprecation notices. These bundled docs match the installed package version and are available without network access.

This block is written and re-added by `turbo` before repository-scoped commands when an AI agent is detected. In the Turborepo source repository, its template is defined in `crates/turborepo-cli/src/cli/agent_guidance.rs`. Removing the managed block while updates are enabled means a later qualifying invocation will add it again. Set `"agentGuidance": false` in the root `turbo.json` or `turbo.jsonc` to opt out; this does not remove an existing block. Keep the block committed with your work to avoid an uncommitted change on the next agent invocation.
